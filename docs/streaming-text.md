# Streaming Text integration

`components/ui/streaming-text.tsx` adapts the supplied 21st.dev Streaming Text component to actual AetherAI replies. The existing shadcn structure, TypeScript alias and Tailwind 4 build are reused. Styles live in `ui/styles.css`, scoped to the component with `n:` utilities; they do not replace the application's colors or reset its CSS. No additional dependencies are required.

`ui/streaming.tsx` mounts and cleans up React roots inside the existing Electron renderer, updates translations and busy state, and builds with the existing `build:ui` pipeline. `streaming-text.js` renders all received text on the next animation frame, supports reduced motion and immediately flushes the full answer on completion. New words fade from blur; code and formulas retain their existing renderer and copy actions.

Sources and inline citation chips come only from actual message URLs. The source count is the number of valid, unique links, rather than the demo's hardcoded count. Sources expand with the supplied grid/opacity transition. Copy writes the real answer to the clipboard. Repeat sends the original question again as a new turn without deleting previous replies. Helpful/not-helpful votes are stored locally on the message and are not sent to providers. Follow-ups retain the existing conditional **Explain in more detail** action and prepare the composer without sending automatically.

The demo's pistachio answer, stock icons, fake sources and repeating animation are not included in chat history. All ten application languages and keyboard access are supported. Run `npm run check`, `npm test`, and the native Electron tests `tests/visual-polish-smoke.cjs`, `tests/answer-visual-smoke.cjs` and `tests/chat-interactions-smoke.cjs`.

Request token usage appears beside the Working/Done label on a shared baseline. Live digits roll as text arrives, with reduced-motion support. Until API usage arrives, `≈` marks a rough text-length estimate (one token per four UTF-16 code units in input plus received answer/reasoning); it excludes image, tool and hidden reasoning costs and is not a billing measurement. It does not grow while no text is arriving. The final count uses actual `usage` fields (including Groq's streamed `x_groq.usage`) and Ollama's `prompt_eval_count` / `eval_count`. Only actual totals are shown in completed replies: missing reports remain unknown, or show `≥` when only a lower total is available. Hover reveals actual input/output totals. Additional agent, tool-selection and fallback calls are aggregated once per request; repeated cumulative reports replace prior counts. No extra billing API requests are used. Reasoning and cache counts are subsets, not extra tokens added to the total.

Provider references: [OpenRouter usage accounting](https://openrouter.ai/docs/cookbook/administration/usage-accounting), [Groq API](https://console.groq.com/docs/api-reference), [Ollama chat metadata](https://docs.ollama.com/api/chat).

Project generation now previews partial JSON manifests and open Markdown file fences as code while tokens arrive. The current file has a localized Writing code label. Preview content is read-only; completed artifacts still pass the existing whole-manifest and save checks. Raw manifest scaffolding is not shown as the final reply after truncation.

File activity is now a collapsed rounded capsule. The disclosure shows real code with line numbers and, when a baseline is known, added/removed lines. Baselines are read before writing and retained locally with the completed activity. Existing-file partial output stays neutral until its content is complete; unsaved and stopped previews retain honest labels.

Files now share a collapsed summary with received file count and trusted change totals. Phases follow actual generation, file-save validation and successful persistence; they do not claim test execution. Actual specialist rows show their task, state and successful completed/total progress. Unknown file baselines and interrupted/unsaved files are never reported as complete changes.
