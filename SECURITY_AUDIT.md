# MultiMind 1.23.0 security review

Reviewed 2026-10-08. This is a scoped source/dependency review, not a guarantee against all vulnerabilities or a penetration test of the deployed database.

Implemented: IPC handlers accept only the registered application main frame at the exact local entry URL; sandbox/context isolation remain enabled; internal remote navigation, child windows and webviews are blocked; renderer CSP forbids inline scripts and frames; external link IPC accepts only HTTP(S) without embedded credentials; project writes reject symbolic links/junctions and traversal; canceled Google exchanges and sign-out during token refresh cannot restore an old session. Credentials reject Linux `basic_text` storage and use restrictive file creation permissions where supported.

Updated Electron, MCP SDK and image dependencies. Both root lockfile and site dependency audit report zero known vulnerabilities at review time. Secret scanning examines publishable text files for common private-key/API-key/service-role-JWT patterns; it is not a proof that every possible secret format is absent. Desktop packaging uses an allowlist. Local auth overrides, email template drafts, backups, private keys, databases and session files are ignored and excluded from packages. The shipped Supabase configuration contains only a public project URL and publishable key.

Live anonymous probe of `multimind_memories`: HTTP 404 / PGRST205, no rows returned. The application table is missing or not exposed through the API. This does not verify other tables, RPCs, Storage buckets, or two-user isolation. Apply `docs/memory-schema.sql` in Supabase SQL Editor: it enables/forces RLS, removes old policies on this application table, revokes public/anon grants, and restricts authenticated CRUD to `auth.uid() = user_id`. Run `docs/database-security-check.sql`, review all other exposed resources, and verify CRUD isolation between two real accounts before enabling production sync. Never ship service-role/secret keys. Revoke any session tokens previously pasted into chat.

Remaining limits: local preset files and chat history are not encrypted. Enabled presets may be sent to the selected cloud model only with explicit consent; switching accounts/models clears consent. Sync is explicit. User-installed stdio plugins run third-party code with the user's OS permissions. Local Ollama/llama.cpp endpoints remain loopback-only but are not authenticated against other processes running as the same user. Packages are unsigned; macOS is not notarized. Google and SMTP configuration remain operator-managed. Browser callback pages contain no tokens and disable caching/external resources.
